# 메모리 실행 개선

## 확인한 원인

B0 LoD2 CDGS 99,493,042개와 B0 ALS CDGS 93,824,742개 삼각형의 원본 성분 정리가 40 GiB 컨테이너 한도 OOM으로 종료됐다. 시작 시점의 호스트 가용 메모리만 점검했고, 메시 크기에 따른 해당 연산의 최대 사용량을 점검하지 않은 것이 실행 관리의 문제였다. 기존 드라이버는 한 프로세스에서 전 채점, 정리, 제거 집계, 후 채점을 이어 수행하며 원본 성분 계산을 제거 집계용으로 반복했다.

## 적용한 실행 변경

- 정리, 전 채점, 제거 집계, 후 채점을 별도 프로세스로 실행한다. 각 프로세스 종료 때 메모리를 반환한다.
- GeoGS 원본 함수와 Open3D의 원본 성분 계산을 그대로 호출한다. Python 프로파일 훅으로 원본 함수 반환 시 성분 배열을 관측해 저장한다. 제거 집계 때문에 원본 메시의 연결 성분을 다시 계산하지 않는다.
- 전체 성분만 제거하고 퇴화 삼각형 제거가 없는 경우, 남은 성분 수와 최소 삼각형 수는 원본 성분 배열의 선택 결과와 같다. 퇴화 삼각형을 지운 경우에는 별도 후처리 프로세스에서 실제 성분을 다시 센다.
- PLY 헤더의 정점·삼각형 수와 관측 최대 사용량으로 사전 실행 계획을 만든다. 추정치가 36 GiB를 넘으면 일반 큐는 실행을 보류한다. 검증용 큰 메시 실행도 기존 잠금과 상한을 지킨다.
- 컨테이너 사용량 38 GiB 또는 호스트 가용 메모리 16 GiB 미만에서 해당 자식 프로세스를 선제 중지한다. OOM 여부·종료 코드·관측 최대 사용량과 완료한 단계를 기록한다. 같은 조건의 실패를 자동 반복하지 않는다.
- 공유 TSDF 잠금, 호스트 가용 56 GiB/60초, 컨테이너 40 GiB·8 CPU, 학습 GPU 우선 조건을 유지한다. 기존 완료 결과·원본 메시·계산 정의를 바꾸지 않는다.

## 검증과 한계

동일 크기 성분과 퇴화 삼각형을 포함한 검증 메시에서 수정 전·후 정점·삼각형·색·법선과 성분 번호·개수·넓이 배열이 일치했다. 메모리를 할당하는 시험 프로세스를 선제 종료해 OOM이 발생하지 않는 것도 확인했다.

최대 메시 B173 LoD2 CDGS(133,038,313개 삼각형)는 2026-10-29 10:40 KST에 약 38.05 GiB에서 선제 중지했다. OOM은 발생하지 않았으나 40 GiB 내 완료를 입증하지 못했다. 원본 알고리즘 자체에 필요한 메모리가 큰 경우 실행 분리만으로 처리할 수 있다고 주장하지 않는다. 이 대상의 동일 조건 재시도는 보류한다. 기존 실패 B0 ALS CDGS를 별도 검증한다.

실측 기록은 tables/mesh_memory_executions.json, 크기별 실행 계획은 tables/mesh_memory_plan.json, 검증 결과는 tables/memory_execution_validation.json 및 tables/memory_guard_validation.json에 있다.
