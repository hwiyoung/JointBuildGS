## 최초 점검 — 입력 묶음 미확인

필요한 파일은 `ALS_sites.npz`, `LoD2_sites.npz`, `sites_summary.json`이다. 발주문이 지정한 해시 앞 16자리는 각각 `2209c54db0112710`, `d769ece96663c34e`, `f28aa9906054fe0f`다. 이 값은 확인 완료를 뜻하지 않는다. 제공된 결과값만 사용해야 하므로 다른 작업의 입력으로 대체하거나 결과값을 새로 구하지 않았다.

현재 학습 컨테이너 두 개가 실행 중이며 각각 약 9.725 GiB와 10.39 GiB를 사용했다. 앞서 22:36에 없던 두 실행이 22:37 이후 시작된 것을 프로세스·컨테이너와 학습 진행 기록에서 확인했다. 이번 점검 중 호스트 여유 메모리는 약 34.32 GiB에서 31.17 GiB로 변했다. 학습은 최근 감소의 직접적인 기여 요인이다. 다만 학습 두 개가 시작되기 전에도 약 51 GiB였으므로 전체 사용량이 학습 두 개 때문이라고 단정하지 않는다.

이전 그림 작업의 준비 과정 최대 프로세스 메모리는 214,088 KiB, 그리기는 707,556 KiB였다. 이는 이번 작업의 최대값을 보장하지 않지만, 64 GiB가 그림 한 장 자체의 실측 필요량은 아님을 보여준다.

시작 기준을 24 GiB로 바꾸고, 컨테이너 4 GiB·프로세서 2개·한 장씩 실행하며, 여유 메모리 16 GiB 미만이나 큰 후처리 시작 시 이 작업만 중단하는 대안을 `configs/phd/main_regionfig_v2/resource_proposal.json`에 작성했다. 기존 학습·후처리에 쓰기나 중단을 요청하지 않는다. 현재 대안은 실행하지 않았고 원래 64 GiB 시작 조건이 여전히 적용된다. 첫 그림에서 이번 작업의 메모리를 실제 확인해야 한다.

## 승인 이후 실행과 표시 수정

사용자가 “응 그래보자”로 자원 변경을 승인했다. `resource_approval.json`에 기록했고, 모든 처리는 GPU 장치 없는 4 GiB 컨테이너에서 실행한다. 첫 그림의 컨테이너 최대 메모리는 428,257,280바이트였다.

첫 시각 점검에서 길게 늘어진 패치를 발견했다. 원본 렌즈 함수가 보정된 시야 밖의 점을 사진 안으로 잘못 투영한 것이 원인이다. 그림 1에서 이런 중심 2,636개를 확인했다. 실제 보정 카메라의 시야 안이라는 조건을 표시와 모든 자른 범위 수치에 똑같이 적용하도록 수정했다. 원본 입력·사진·자른 상자·회전·단면은 그대로다. 수정 전 산출물은 외부 작업 폴더의 `revision_01/`에 보존하고 수정 시각과 해시를 설정 폴더에 남겼다.

첫 수정 실행은 사진 너비 변수 이름과 원본 자료 경로 이름이 겹쳐 `UnboundLocalError`로 실패했다. 변수 이름을 고쳤다. 실패 로그와 영수증을 보존했다. 이 실패는 학습이나 원본 입력에 영향을 주지 않았다.

## 최종 확인

범례에 영역 이름의 뜻을 덧붙이고, 상속 가운데 사전 정보가 틀린 단면 띠의 빗금을 보완했다. 그림 5·6의 독립 점검자 네 명의 답 전문과 범례 보완 전 그림을 보존했다. 두 명의 재점검에서 뜻의 모호함이 줄고 새 글자 겹침은 없음을 확인했다. 축소 화면의 작은 범례, 반투명 색으로 가려지는 사진 세부, 같은 높이에서 겹치는 단면 선은 남은 표시 한계다. 색칠 없는 원본 조각을 함께 제공한다.

최종 검증은 원본 입력으로 비율을 따로 구하고, 원본 사진 화소·동일 사진 캔버스·단면 전체의 자른 상자 포함·단면 중앙값·상속 값·설정 잠금 시각을 확인했다. 192개가 모두 통과했다. 검증 전체 기록은 `tables/verification.json`에 있다. 과학적 판정은 하지 않는다.

재현 기록 작성의 첫 실행은 Docker 안에서 외부 worktree의 Git 관리 경로에 접근할 수 없어 실패했다. 호스트 런처가 읽기 전용으로 확인한 커밋을 환경값과 영수증에 전달하도록 고쳤다. 실패 영수증은 보존한다. 재현 문서가 없는 첫 압축 실행은 납품본으로 사용하지 않으며, 문서를 완성한 뒤 모든 압축 파일과 해시를 다시 만든다.

마지막 자원 설정 확인에서 I/O 유휴 우선순위가 호스트 Docker 명령에만 적용된 것을 확인했다. 재현 기록과 최종 압축 실행부터 컨테이너 안의 처리에도 직접 적용했다. 앞선 그림·검증에도 메모리 상한 4 GiB, 프로세서 2개, CPU 우선순위 19와 메모리·후처리 감시는 적용돼 있었다. 실제 최종 처리의 CPU·I/O 우선순위는 재현 숫자 파일에 기록한다.
