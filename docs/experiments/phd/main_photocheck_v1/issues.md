# 확인 불가와 예외

- 전체 단계 초기에 프로세스가 사진 파일 읽기를 기다리는 상태와 긴 실제 시간이 확인됐다. 첫 큰 타일의 사진 묶음은 LoD2에서 9.86~13.33GB, 항공 LiDAR에서 18.22~19.04GB였다. 컨테이너 안의 `/out/tmp/image_cache_ram`에 최대 20GiB의 임시 바이트 캐시를 추가했다. 컨테이너 전체 제한은 32GiB이고 영구 사진 캐시는 보존했다. 표본 파일의 SHA-256이 같음을 확인했으며, 완료된 타일을 저장한 뒤 이어서 적용했다. 계산 규칙·화소 값은 같다. [이 발주에서 냄]

- `s_mvs`는 MVS 높이에서 가장 가까운 표본 높이의 점수다. 그 높이의 점수가 없을 때 다른 높이의 유효 점수로 건너뛰던 코드를 고쳤다. 시범 48점은 `s_mvs`만 누락값으로 고쳤으며 앞 값과 점 번호를 별도 보존했다. 곡선과 15가지 판단, 투영 점검에는 변화가 없다. [이 발주에서 냄]
- R1의 좁은 틈 예시는 원본 사진과 사전 정보 면 323의 기하를 보고 별도 두 좌표를 고정했다. 곡선이나 참값을 보며 점을 고르지 않았다. 기록은 `figure_site_supplement.json`과 잠금 파일에 있다.

- 같은 항공 LiDAR 면이 여러 건물에 걸친 개발 영역 105개 면에서, 처음 코드가 건물별로 격자 원점을 다시 잡던 차이를 코드 점검으로 발견했다. 발주문의 면별 원점으로 고쳤다. 기존 항공 LiDAR 점 묶음과 시범 값은 무효 기록으로 보존하고 다시 구했다. 한 점의 건물이 여럿이면 모든 건물 번호를 남기며, 표는 원래 패치의 건물 번호를 쓴다. 개발·확인용 경계만 별도 점으로 나눈다. LoD2는 면마다 건물이 하나여서 기존 계산이 그대로다.

- CPU와 GPU 시간 측정이 같은 사진 캐시를 동시에 만들 때, GPU가 아직 완성되지 않은 파일을 읽어 첫 측정이 중단됐다. 캐시는 임시 파일을 완성한 뒤 한 번에 이름을 바꾸도록 고쳤다. 중단된 측정은 시간 어림과 판단에 쓰지 않는다. 설정과 입력 자료에는 변화가 없다.
- 캐시를 고친 뒤 CPU·GPU 256점의 3,840개 판단은 모두 같았지만, 저장 곡선의 최대 차가 0.00314331이었다. 본 시범 전에 투영 좌표 계산만 64비트로 높였다. 설정의 앞 값과 해시를 `photocheck_v1_r0`에 보존했고 변경 시각과 까닭을 잠금 기록에 남겼다. 후보 값·사진 선택·판단 규칙은 같다.

- 원본 지붕 패치 가운데 1,698개는 법선이 정의되지 않았다. 원본을 보존하고 점의 기하 정보가 없다고 기록한다. 사진을 고르거나 참값으로 법선을 채우지 않는다. [이 발주에서 냄]
- 가려짐은 넓히기 v2의 타일별 등록 이동을 적용한 같은 메시로 구한다. 메시의 주변 범위는 앞 작업의 10m이며 그 밖에 표현되지 않은 사전 정보는 가려짐 계산에 없다.
- 높이별 가려짐은 다시 구하지 않는다. 사진 집합은 사전 정보 높이에서 한 번 고정한다.
- 사전 정보 불확실도가 없으면 범위 안·밖 비교는 확인 불가이며 모름(애매)으로 남긴다. 곡선과 원래 누락 상태를 보존한다.
- 한 사진 조각의 밝기 분산이 0이면 그 조각과의 상관은 정의되지 않는다. 해당 높이의 점수를 비우고 사진별 무늬의 세기와 0분산 사진 수를 남긴다.
- 넓히기 v2 그림 코드에서 명시된 칸 색은 1번 파랑 `#0072b2`, 2번 주황 `#d55e00`이다. 두 색을 그대로 사용한다. 나머지 다섯 칸의 기존 고정 색은 확인 불가여서 보조색과 칸 번호를 함께 표시한다. 칸 번호와 값은 바꾸지 않는다.

- 그림 출력 지연을 점검한 보기점 한 개에서 78.99초 중 자료형 변환에 74.60초가 쓰였다. 대체 변환을 별도로 검사해 0~255의 모든 입력값·세 색 채널과 사진 배열 8개의 SHA-256 일치를 확인했다. 이 검사를 진행하는 동안 전체 그림 생성이 끝나, 대체 변환은 전달하는 측정값·그림 생성에 적용하지 않았다. `profile_figure.py`, `verify_fast_cast.py`와 해당 실행 기록은 참고 진단이다. [이 발주에서 냄]
